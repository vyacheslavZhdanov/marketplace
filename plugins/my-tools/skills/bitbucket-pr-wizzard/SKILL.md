# Bitbucket PR Wizzard

## Overview

Создаёт Bitbucket Pull Request с контекстом из Jira и анализом diff через Bitbucket MCP.

**Репозиторий:** `sl-android` (workspace: `sunlight_team`)

## Requirements

### MCP-инструменты

| Инструмент | Назначение |
|---|---|
| `mcp__atlassian__getJiraIssue` | Получение summary и URL Jira-задачи |
| `mcp__bitbucket__create_pull_request` | Создание PR в Bitbucket |
| `AskUserQuestion` | Интерактивный выбор целевой ветки и согласование описания |

### Предусловия окружения

- Наличие доступа к Jira (Atlassian MCP настроен и аутентифицирован)
- Наличие доступа к Bitbucket (Bitbucket MCP настроен и аутентифицирован)
- Текущая ветка содержит номер задачи в формате `ECO-XXXX`
- Репозиторий: `sl-android`, workspace: `sunlight_team`

## Шаги

### 1. Сбор информации

#### 1а. Jira-задача

Извлеки номер задачи из названия текущей ветки (формат `ECO-XXXX`):

```bash
git branch --show-current
```

Получи summary задачи и её URL через `mcp__atlassian__getJiraIssue`.

#### 1б. Целевая ветка

Сначала автоматически определи ветку ветвления:

```bash
git log --oneline --decorate -30
```

Найди первый коммит с меткой другой ветки — это точка ветвления (`<АВТО ВЕТКА>`).

Затем задай вопрос пользователю через `AskUserQuestion` с двумя опциями:

```
Вопрос: «Выбери целевую ветку для PR»
Опции:
  1. master
  2. <АВТО ВЕТКА>  ← подставь реальное имя ветки
```

- Если **1** — используй `master`.
- Если **2** — используй `<АВТО ВЕТКА>`.
- Если пользователь ввёл своё значение через "Other" — используй его.

#### 1в. Изменения

После определения целевой ветки получи diff:

```bash
git diff <ЦЕЛЕВАЯ ВЕТКА>...HEAD --stat
git diff <ЦЕЛЕВАЯ ВЕТКА>...HEAD
```

### 2. Проверь незакоммиченные / незапушенные изменения

```bash
git status
git log origin/<ТЕКУЩАЯ ВЕТКА>..HEAD 2>/dev/null || git log --oneline -5
```

Если есть незакоммиченные изменения или коммиты, не отправленные в remote — **сообщи пользователю** и предложи сделать коммит/пуш перед созданием PR. Дожидайся подтверждения или отказа, прежде чем продолжать.

### 3. Подготовь описание PR и согласуй с пользователем

На основе summary из Jira и diff сформируй:
- **Заголовок** по формату из раздела «Формат PR»
- **Описание** по формату из раздела «Формат PR»

Покажи пользователю подготовленный заголовок и описание. Спроси: нужны ли правки?

Если да — внеси правки согласно пожеланиям и покажи снова. Повторяй, пока пользователь не подтвердит.

### 4. Запушь ветку и создай PR

После подтверждения описания запушь ветку:

```bash
git push -u origin HEAD
```

Затем создай PR через `mcp__bitbucket__create_pull_request`:

```
repo_slug: "sl-android"
title: "<СФОРМИРОВАННЫЙ ЗАГОЛОВОК>"
source_branch: "<ТЕКУЩАЯ ВЕТКА>"
destination_branch: "<ЦЕЛЕВАЯ ВЕТКА>"
description: "<ОПИСАНИЕ>"
close_source_branch: true
```

### 5. После создания

Выведи пользователю:
- Ссылку на созданный PR
- Заголовок PR
- Описание PR

## Формат PR

**Заголовок:** `<НОМЕР ЗАДАЧИ>: <SUMMARY ЗАДАЧИ ИЗ JIRA>`

Берётся как есть, без преобразований.

**Примеры:**

| Jira summary | Заголовок PR |
|---|---|
| `SL Android, Arch - Добавить стратегии` | `ECO-12272: SL Android, Arch - Добавить стратегии` |
| `[Android] Заменить дизайн информеров` | `ECO-12355: [Android] Заменить дизайн информеров` |

**Описание:**
```
<ССЫЛКА НА ЗАДАЧУ В JIRA>

Изменения:

- <буллит 1: что добавлено/изменено и зачем>
- <буллит 2>
```

## Правила составления описания

- Каждый буллит — одно логическое изменение, не файл
- Названия классов/методов в `backticks`
- Писать на **русском языке**
- Без технических деталей реализации — только суть изменений
- По минимуму ссылаться на классы/методы, описывать не техническим языком
- Только основные изменения
- **Пустая строка перед списком** — иначе Bitbucket не рендерит буллиты как markdown-список

## Частые ошибки

| Ошибка                                  | Как исправить                                                                                    |
|-----------------------------------------|--------------------------------------------------------------------------------------------------|
| Анализ только последнего коммита        | Смотреть весь diff от целевой ветки до HEAD                                                      |
| Описание файлов вместо изменений        | Каждый буллит = логическое изменение                                                             |
| Технические детали в описании           | Только внешне наблюдаемые изменения                                                              |
| Английский язык в описании              | Переключить на русский                                                                           |
| `\n` в description вместо переноса      | В параметре `description` MCP-инструмента использовать реальные переносы строк, а не литерал `\n` |
| Буллиты не рендерятся как список        | Перед первым `- ` должна быть пустая строка                                                      |
