# Документирование Kotlin-кода

## Обзор

Документация должна объяснять **смысл и контракт**, а не пересказывать код. Хорошая документация — та, без которой читателю было бы сложно понять: зачем нужен этот класс, что гарантирует этот метод, и как правильно его использовать.

**Руководства:** [Android KDoc Guidelines](https://android.googlesource.com/platform/frameworks/support/+/refs/heads/androidx-main/docs/kdoc_guidelines.md) · [Kotlin KDoc](https://kotlinlang.org/docs/kotlin-doc.html)

## Что документировать

| Видимость | Когда документировать |
|---|---|
| `public` | Всегда. Без исключений. |
| `internal` | Только если неочевидно назначение или поведение |
| `protected` | Только если неочевидно назначение или поведение |
| `private` | Только если сложная логика требует пояснения |

**Build-скрипты** (`.gradle.kts`, `build.gradle.kts`) — не документировать.

## Правило очевидности

Если смысл полностью понятен из имени — документация не нужна. Исключение: если метод оборачивает метод Android SDK — добавить `@see`, даже без основного текста.

```kotlin
// ❌ Очевидно — не писать текст
/** Перезагружает страницу */
fun reload()

// ✅ Очевидно, но оборачивает SDK — добавить @see
/** @see [android.webkit.WebView.reload] */
fun reload()

// ✅ Неочевидно — документировать
/**
 * Возвращает назад, сохраняя промежуточное состояние формы.
 * Если стек пуст, завершает экран.
 */
fun goBack()
```

## Что писать в документации

**Для классов и интерфейсов:**
- Зачем нужен (роль в архитектуре, контракт)
- Какие гарантии предоставляет
- Ограничения использования

**Для функций:**
- Что делает и какой результат возвращает (если неочевидно)
- Побочные эффекты
- Предусловия и постусловия
- `@param` — только если роль параметра неочевидна из имени
- `@return` — только если возвращаемое значение неочевидно
- `@throws` — если выбрасывает исключение
- `@see` — если метод оборачивает или соответствует конкретному методу Android SDK

**Для свойств:**
- Что хранит, если неочевидно из имени
- Особенности жизненного цикла или потокобезопасности

**Важные заметки и предупреждения** оформлять blockquote-синтаксисом:

```kotlin
/**
 * Возвращает `true`, если доступен переход назад по истории.
 *
 * > Рекомендуется вызывать перед [goBack].
 */
fun canGoBack(): Boolean
```

## Изоляция документации

Документация описывает **контракт**, а не реализацию.

```kotlin
// ❌ Плохо — ссылка на реализацию из интерфейса
/**
 * Загружает данные. Реализован в [ProductRepositoryImpl].
 * Внутри использует Retrofit и кэш Room.
 */
interface ProductRepository {
    suspend fun getProducts(): List<Product>
}

// ✅ Хорошо — только контракт
/**
 * Репозиторий для получения каталога товаров.
 * Гарантирует актуальность данных на момент вызова.
 */
interface ProductRepository {
    suspend fun getProducts(): List<Product>
}
```

**Запрещено в документации:**
- Упоминать конкретные классы-реализации интерфейса
- Описывать детали реализации (Retrofit, Room, конкретный алгоритм)
- Описывать, что произойдёт "внутри"

## Язык

**Русский** — основной язык документации.

**Английский** допускается для:
- Имён классов, функций, полей: `[ProductRepository]`, `currentUser`
- Устоявшихся терминов: `suspend`, `coroutine`, `Flow`, `ViewModel`
- Алгоритмов и паттернов: `LRU cache`, `Builder pattern`

```kotlin
// ✅ Правильно
/**
 * Состояние экрана каталога товаров.
 * Используется как единый источник правды для Compose UI.
 */
data class CatalogUiState(...)

// ❌ Неправильно
/**
 * Catalog screen state.
 */
data class CatalogUiState(...)
```

## Контекст перед написанием

Перед написанием документации необходимо:

1. **Понять, кто вызывает** этот код — найти usages
2. **Понять, кто наследует** — для интерфейсов и абстрактных классов
3. **Понять жизненный цикл** — особенно для компонентов с состоянием
4. **Понять ограничения** — потокобезопасность, вызов только с main thread и т.д.

Без этого контекста документация будет неполной или вводящей в заблуждение.

## Частые ошибки

| Ошибка | Как исправить |
|---|---|
| Документация пересказывает код | Объяснять **зачем**, а не **что** |
| KDoc на очевидный метод | Убрать документацию |
| Ссылка на реализацию из интерфейса | Описывать только контракт |
| Описание деталей реализации | Оставить только внешне наблюдаемое поведение |
| Английская документация | Переключить на русский |
| `@param` для очевидного параметра | Убрать `@param`, имя говорит само за себя |

## Пример качественной документации

```kotlin
/**
 * Менеджер навигации WebView, отслеживающий историю переходов.
 *
 * Предоставляет возможность программной навигации вперёд/назад
 * и уведомляет о смене текущего URL через [currentUrl].
 *
 * Не является потокобезопасным — все вызовы должны выполняться
 * на главном потоке.
 */
interface WebPageNavigator {

    /** Текущий URL загруженной страницы, или `null` если страница не загружена. */
    val currentUrl: StateFlow<String?>

    /**
     * Возвращает, доступен ли переход назад по истории.
     * Использовать перед вызовом [goBack] для проверки.
     */
    val canGoBack: Boolean

    /** Переходит назад по истории браузера. Вызывать только если [canGoBack] == `true`. */
    fun goBack()
}
```
