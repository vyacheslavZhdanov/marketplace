# Forgejo PR Wizzard

## Overview

Создаёт Pull Request в Forgejo с контекстом из Jira и анализом diff через мини-CLI `scripts/forgejo.py`, который лежит в папке скилла (`${CLAUDE_SKILL_DIR}`).

**Репозиторий:** определяется по `git remote origin` (для этого проекта — `GRI_Android/sunlight` на `git.global.internal`).

## Requirements

### Инструменты

| Инструмент | Назначение |
|---|---|
| `mcp__atlassian__getJiraIssue` | Получение summary и URL Jira-задачи |
| `python "${CLAUDE_SKILL_DIR}/scripts/forgejo.py"` | Проверки и создание PR в Forgejo (`--help` — все команды) |
| `AskUserQuestion` | Интерактивный выбор целевой ветки (НЕ для согласования описания) |

### Предусловия окружения

- Доступ к Jira (Atlassian MCP настроен и аутентифицирован)
- Python 3 (скрипт использует только stdlib)
- В корне git-репозитория проекта (папка `.secrets/` должна быть в `.gitignore`):
  - `.secrets/forgejo.json` — `{"url": "https://git.global.internal", "username": "<логин>", "token": "<токен Forgejo>"}`
  - `.secrets/gri-ca.pem` — CA-цепочка GRI (другой путь можно задать полем `"ca_file"` в конфиге)
- Проверка: `python "${CLAUDE_SKILL_DIR}/scripts/forgejo.py" whoami` (запускать из папки проекта)
- Текущая ветка содержит номер задачи в формате `ECO-XXXX`

`fj` и `curl` для Forgejo **не использовать**: на этой машине им не доверен корпоративный сертификат, работает только `forgejo.py` из скилла.

## Шаги

### 1. Сбор информации

#### 1а. Jira-задача

Извлеки номер задачи из названия текущей ветки (формат `ECO-XXXX`):

```bash
git branch --show-current
```

Получи summary задачи и её URL через `mcp__atlassian__getJiraIssue`.

#### 1б. Целевая ветка

Сначала автоматически определи ветку ветвления:

```bash
git log --oneline --decorate -30
```

Найди первый коммит с меткой другой ветки — это точка ветвления (`<АВТО ВЕТКА>`).

Затем задай вопрос пользователю через `AskUserQuestion` с двумя опциями:

```
Вопрос: «Выбери целевую ветку для PR»
Опции:
  1. master
  2. <АВТО ВЕТКА>  ← подставь реальное имя ветки
```

- Если **1** — используй `master`.
- Если **2** — используй `<АВТО ВЕТКА>`.
- Если пользователь ввёл своё значение через "Other" — используй его.

#### 1в. Изменения

После определения целевой ветки получи diff:

```bash
git diff <ЦЕЛЕВАЯ ВЕТКА>...HEAD --stat
git diff <ЦЕЛЕВАЯ ВЕТКА>...HEAD
```

### 2. Проверь незакоммиченные / незапушенные изменения

```bash
git status
git log origin/<ТЕКУЩАЯ ВЕТКА>..HEAD 2>/dev/null || git log --oneline -5
```

Если есть незакоммиченные изменения или коммиты, не отправленные в remote — **сообщи пользователю** и предложи сделать коммит/пуш перед созданием PR. Дожидайся подтверждения или отказа, прежде чем продолжать.

### 3. Подготовь описание PR и согласуй с пользователем

На основе summary из Jira и diff сформируй:
- **Заголовок** по формату из раздела «Формат PR»
- **Описание** по формату из раздела «Формат PR»

Выведи заголовок и описание полным текстом (markdown-блоками) **финальным сообщением хода**, в конце — строка «Создавать PR? (да / правки)», и **заверши ход**. Дальше ждёшь ответа пользователя в чате.

**`AskUserQuestion` на этом шаге НЕ использовать.** Текст, выведенный перед вызовом инструмента, перекрывается диалогом вопроса — пользователь его не видит. Описание должно быть последним, что пользователь видит в ответе.

Если нужны правки — внеси их и снова выведи полный текст заголовка и описания тем же способом. Повторяй, пока пользователь не подтвердит.

### 4. Запушь ветку и создай PR

После подтверждения описания запушь ветку:

```bash
git push -u origin HEAD
```

Сначала прогони создание с `--dry-run` — скрипт проверит, что ветка есть на сервере, совпадает с локальной и что из неё ещё нет открытого PR. Описание передавай через heredoc с `'EOF'` в кавычках — так shell не тронет backticks и `$`:

```bash
python "${CLAUDE_SKILL_DIR}/scripts/forgejo.py" pr create --base "<ЦЕЛЕВАЯ ВЕТКА>" \
    --title "<СФОРМИРОВАННЫЙ ЗАГОЛОВОК>" --body-file - --dry-run <<'EOF'
<ОПИСАНИЕ>
EOF
```

Если dry-run прошёл без ошибок и предупреждений — повтори ту же команду **без** `--dry-run`. Если скрипт сообщил об ошибке или предупреждении (ветка не найдена, расходится с локальной, PR уже открыт) — покажи сообщение пользователю и не создавай PR.

`--head` не нужен — берётся текущая ветка. Ревьюеров (`--reviewer LOGIN`) добавляй, только если пользователь их назвал; логины Forgejo ищутся через `python "${CLAUDE_SKILL_DIR}/scripts/forgejo.py" api GET 'users/search?q=<фамилия>'`.

### 5. После создания

Сразу после успешного создания, **без дополнительного запроса от пользователя**, выведи текстовым сообщением в чат:
- Ссылку на созданный PR (последняя строка вывода `pr create`)
- Заголовок PR
- Описание PR

Затем проверь статус мёржа (`python "${CLAUDE_SKILL_DIR}/scripts/forgejo.py" pr view <N>`, строка «Статус») и, если там «конфликты», сообщи об этом.

Это финальный шаг скилла — не завершай ответ без него.

## Формат PR

**Заголовок:** `<НОМЕР ЗАДАЧИ>: <SUMMARY ЗАДАЧИ ИЗ JIRA>`

Берётся как есть, без преобразований.

**Примеры:**

| Jira summary | Заголовок PR |
|---|---|
| `SL Android, Arch - Добавить стратегии` | `ECO-12272: SL Android, Arch - Добавить стратегии` |
| `[Android] Заменить дизайн информеров` | `ECO-12355: [Android] Заменить дизайн информеров` |

**Описание:**
```
<ССЫЛКА НА ЗАДАЧУ В JIRA>

Изменения:

- <буллит 1: что добавлено/изменено и зачем>
- <буллит 2>
```

## Правила составления описания

- Каждый буллит — одно логическое изменение, не файл
- Названия классов/методов в `backticks`
- Писать на **русском языке**
- Без технических деталей реализации — только суть изменений
- По минимуму ссылаться на классы/методы, описывать не техническим языком
- Только основные изменения
- **Пустая строка перед списком** — иначе markdown может не отрендерить буллиты как список

## Частые ошибки

| Ошибка | Как исправить |
|---|---|
| Анализ только последнего коммита | Смотреть весь diff от целевой ветки до HEAD |
| Описание файлов вместо изменений | Каждый буллит = логическое изменение |
| Технические детали в описании | Только внешне наблюдаемые изменения |
| Английский язык в описании | Переключить на русский |
| Описание через `--body "..."` с backticks | Использовать `--body-file -` и heredoc `<<'EOF'` |
| Создание PR без dry-run | Сначала `--dry-run`, потом реальный вызов |
| Попытка использовать `fj`/`curl` | Только `forgejo.py` из скилла — им доверен CA GRI |
| `api GET /users/...` с ведущим `/` в Git Bash | Писать путь без ведущего `/`: `users/search?q=...` |
| Ожидание `close_source_branch` как в Bitbucket | В Forgejo удаление ветки выбирается при мёрже, при создании PR не задаётся |
